# 签名来源信任与精确版本 registry

M4 之后先实现来源认证、接收方信任与撤权，再接入网络交换。发布采用 Ed25519 签名，覆盖协议域、分享包摘要及 team/publisher/key 身份；接收方按公钥指纹独立登记身份绑定，包不能自授信任。公钥身份以 SPKI 内容摘要固定，已撤销密钥永久保留撤销状态；轮换必须生成并独立登记新公钥。使用 Node 原生密码学，遵循其 [Ed25519 签名与验证合同](https://nodejs.org/api/crypto.html#cryptosignalgorithm-data-key-callback)，避免增加自制算法或外部签名服务。

签名包继续使用 M4 白名单内容与完整依赖校验；签名来源证明与导入版本在同一事务保存。新导入、继承、评估与首次晋升都检查当前公钥信任，撤信不能被幂等导入绕过。已经提交的晋升按 operationId 读回；已采用行为和历史证据不自动回滚或删除。签名只证明持钥发布身份，不能证明内容安全、评估有效或授予接收方运行权限。旧 unsigned 离线包仍支持操作者主动导入，网络 registry 路径严格要求签名。

Registry 采用精确摘要寻址的不可变 PUT/GET，沿用 SQLite 与 blob 持久化，不提供 latest、搜索或自动升级。服务端独立登记可信发布公钥；写入同时需要绑定团队及既有主体权限的随机 bearer 凭据，team 包读取需要 read 凭据，public 包允许匿名读取。凭据只保存摘要，撤销 token、撤销团队授权与撤销来源密钥在每次请求时检查；团队未授权读取及已撤信发布返回 404。服务端信任不替代接收方信任，下载后仍执行签名验证、本地评估与显式晋升。

客户端限制请求/响应大小与总超时，拒绝重定向，不自动重试写入；远端只能使用 HTTPS，HTTP 仅用于 loopback。CLI 服务仅监听 loopback，由部署者配置 HTTPS 反向代理；本轮验证实际本机 HTTP 协议与持久化恢复，未部署外网服务。私钥与凭据文件使用 0600，不进入分享包、调用日志或事件；公钥与指纹必须通过操作者信任的渠道核对，TLS 或首次收到的公钥本身不能替代身份确认。

Kernel 新增显式授权撤销，Runtime 在新决策发送与执行派发事务中重新检查当前组织、版本闭包和固定裁判权限。撤权阻止后续派发，未发送调用结案并释放额度；已经发出的调用及外部结果保留真实或未知证据。已在执行的工作不被本轮强制中止，后续节点和重试不再获得旧授权。大规模联邦、证书基础设施、自动密钥发现、远程运行调度与共进化仍需后续独立设计。
