# 固定输出上限对照 v1（O2-R1）

2026-10-28。用户要求提高上限并按顺序验证。原八条件矩阵在 142/160 时收到服务 HTTP 500 `overloaded_error`，按原协议封闭，新增未知用量 1 次，筛选结果为空。该轮保持 incomplete，不补考、不重发、不视为 O2-02 或原 O2-03 通过。

本协议在看到部分矩阵结果后单独登记，直接回答“旧布局、零示例下，将输出上限由 256 提高到 512 是否改善效果”。它不是合格矩阵候选的确认，也不作为示例或编译收益证明。

## 固定设计

- `routing-fixed-output-v1`，20 个新的开发任务、10 个模板 family ×2 资料变体；两个目标能力各半，4 个预标记关键任务。
- 两条件固定为旧 v1 布局、零示例的 512 与 256；除输出额度外，实际请求、组件和执行条件一致。每任务每条件 3 repeats，共 **120 次生成**，顺序按冻结 seed 轮转。
- 使用既有确认开发资料，该资料尚未向真实服务派发。任务、输入、标签/期望 JSON、配置、额度与错误处理在首次请求前冻结；标签不进入模型输入。
- 单次 Run 30 秒，决策 28 秒，SDK 重试 0；输入同正文预检 ≤2,048 并核对实际用量。全段派发时限为 120×30 秒加 300 秒收尾，不足完整窗口不领取新槽位。

## 服务错误策略

该规则是对已见服务 500 的明确新登记，不修改原矩阵的“未知即停止”规则。

生成已经开始且 SDK 返回明确 HTTP 500/502/503/504 时，最多 **2 个既定槽位**可封为失败、用量未知并继续后续已登记槽位。未知占用不返还、不重发、不会增加重复次数；同一任务原先登记的其他 repeat 仍保留各自分母。第三次 5xx 停止。

计数 API 错误、取消/超时、身份异常、成功响应的用量缺失/超限/漂移、结束元数据缺失等不在容错范围，仍立即停止。HTTP 状态来自受信 SDK 异常字段，不根据模型自述推断。父轮原始报告须复算一致，并核验其最后一个生成调用确实以服务 5xx 失败；旧槽位和成本不改写。

## 判定与成本

以完整 60 单元/条件分母、family 等权报告真实 worker 验收、合法 JSON、误派、结束原因、延迟及全部用量。未知与服务错误算失败，缺失不删除。对照仅输出上限，不搜索示例、模型、布局或任务。

严格的 `confirmationPassed` 仍须当前阶段计量全部完整、合法 JSON ≥95%、实际成功 ≥90%、关键任务全过，相比 256 成功率至少提高 5 个百分点。若有容忍的服务错误，则 `engineering=incomplete`、`confirmationPassed=false`，可以单列以全分母计算的描述性质量门；不得把它写成严格确认通过。真实模式 `benefit=inconclusive`，无正式 Evaluation 或自动采用。

原 O1 共 793 次，原矩阵已消费 142 次（含未知），本段最多 120 次，累计开发 **262/280 次**、含 O1 历史 **1,055 次**。未派发的 18 个矩阵槽位保留在原计划分母；不是给已发送未知退还额度。父历史未知 2 次继续单列，费用/币种未核验时保持 unknown。

真实运行要求干净提交、新目录、新 ID：

```bash
env PATH="/opt/homebrew/bin:$PATH" /opt/homebrew/bin/node \
  tests/experiments/run-diagnostic.ts --real --output NEW_DIRECTORY \
  --parent SEALED_STOPPED_MATRIX_DIRECTORY --stage fixed-output \
  --claude-settings /path/to/explicit/settings.json
```

只复制封闭父实例，不执行旧 Run。当前固定对照通过也只支持输出上限的开发改进；原矩阵和示例筛选门未通过，不进入原 O2-03 / O2-04 或 M6b/M6c。下一步依据新的完整观测决定基线配置与后续实验。
