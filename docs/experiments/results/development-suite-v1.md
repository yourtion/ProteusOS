## 暴露出的验收缺口

快照任务三次均正确移除了摘要对 version ID 的依赖，却同时把原来的 `import type ... from './types.ts'` 改成了自行推测的内联类型。

- 第 1 次把 `Principal.kind` 从固定联合类型放宽成 string，并丢掉 `Artifact.ownerId`；普通仓库类型检查可通过，但公开类型契约已经变化。
- 第 2 次把 PrincipalKind 猜成 `human | service | system`；第 3 次猜成 `user | service`。二者都与原有 `user | organism | team` 调用方不兼容，历史仓库类型检查直接失败。
- 三次都能通过针对摘要函数的 5 项行为检查。这证明当前函数级检查无法代表仓库集成正确性。

这是**事后新增的兼容性复核**，不回改冻结协议的 9/9 功能成绩。它在各自历史仓库 src 和原 tsconfig 中替换一个候选文件，并对 kernel 六个公开领域类型增加与原类型定义的一致性断言。三个原始仓库基线全部通过；候选结果为 6/9 通过。完整诊断见 [type-review.json](./development-suite-v1/type-review.json)。通过此项也不等于无条件可合入；仍需任务对应回归和代码审查。

从可见补丁可以确认类型被改写；“单文件输入没有给出类型依赖，完整文件输出要求促使模型补全未知定义”是当前解释，需要下一轮受控验证。现阶段不把失败归结为模型能力不足，也不靠增加 token 上限解决验收问题。

## 下一轮执行顺序

1. **先升级验收。** 在一次性历史仓库副本里运行类型检查，并固定公开接口契约和必要回归。把本轮三份 snapshot 坏补丁作为反例：新验收必须拒绝，原历史修复必须通过。验收尚未升级前维持人工审查，不自动合入。
2. **再改善输入与修改方式。** 显式提供任务必需的类型依赖，限定可写文件；保留原类型导入，给候选准备原文件副本后允许最小编辑，避免要求模型重建未知定义。只改变这组因素，固定模型、预算和验收重跑 snapshot 任务；原始结果继续保留。新依赖文件和新调用预算另行确认后执行。
3. **通过后再扩任务。** 增加不同模块和真实开发任务，覆盖调用方集成、错误处理等问题；按独立任务统计，通过率、延迟、tokens 和人工修订量一起报告。更大规模之前不把 3 个历史缺陷的重复成功视为通用开发能力。
